# マッチングルール

## 基本思想

求人の意味に沿ったタグ候補を安定して抽出する。誤爆コストが高い項目は保守的に扱う。

## グローバル設定

機械可読な既定値は `config/matching-defaults.json` を参照する。

### 短いASCIIトークン

`token_exact` と3文字以下のASCII aliasは、大小を無視しつつraw substringではなく境界一致する。

基本形:

```text
(?<![A-Za-z0-9_])TOKEN(?![A-Za-z0-9_])
```

日本語はASCII token文字に含めないため、`生成AI` / `AI活用` / `STスタッフ` は一致する。一方、`mail` 内のAI、`staff` 内のSTは一致しない。

この仕様では `OpenAI` 内のAIは自動一致しない。必要ならOpenAIを別aliasとして明示的に追加する。

### 可 / OK の「も」

canonical / strict aliasの末尾が `可` または `OK` の場合だけ、直前の `も` を任意として扱う。

- `車通勤可` → `車通勤も可` も一致
- `副業OK` → `副業もOK` も一致

「も」を文章全体から削除するような正規化は禁止。

## 今回追加した代表alias

- `例外事由3号イ` → `例外事由3号のイ` / `例外事由3号 イ`
- `U・Iターン歓迎` → `UIターン歓迎` / `U/Iターン歓迎` / `Uターン・Iターン歓迎`
- `三交代制` → `三交代` / `3交代` / `三交替` / `3交替` など
- 二交代制も同じ規則で補強
- PT / OT / ST → 理学療法士 / 作業療法士 / 言語聴覚士のloose alias

## match_policy

### normal
canonical / alias_strictを通常判定する。

### context
単語だけで意味や関係性が確定できないタグ。

### pattern
数値・形式・閾値で判断する。

### token_exact
短い英数字タグをASCII token境界で判定する。

### strict_only
予約済み。

## alias_loose

loose aliasは近い意味・業界略語などを保持するが、文脈次第で別意味になり得る。PT / OT / STのような短縮語はtoken境界に加え、必要に応じて医療・リハビリ文脈を確認する。

## alias_strict / alias_loose の運用補足

`alias_strict` は完全な言い換えだけでなく、**その表現があればcanonicalの条件を確実に満たす表現**まで含める。

例:

- `社員割引あり` → `社割あり`
- `日勤専従` → `夜勤なし`
- `寮あり` → `寮・社宅あり`

ただし、別canonicalが存在する場合は安易に統合しない。

例:

- `食費補助あり` と `食事補助あり` は別canonicalとして存在するため相互aliasにしない。
- `食費補助あり` には `食事代補助` のみ追加する。

`alias_loose` は関連性が高いが、自動確定には意味が広い表現に使う。

例:

- `短期3ヶ月` → `短期（3ヵ月以内）` のreview候補
- `ディーラー` → `クルマ販売店` のreview候補
- `PC入力` / `キーボード入力` → `タイピング` のreview候補

## 表記揺れの横断ルール

第3版では全1,617タグを再走査し、別canonical・別aliasとの衝突がない場合に限り、次の表記揺れをstrict aliasとして補強した。

- `ヵ月 / ヶ月 / か月`
- `祝い金 / 祝金`
- `引っ越し / 引越し / 引越`
- `組み立て / 組立て / 組立`
- `持ち込み / 持込み / 持込`
- `問い合わせ / 問合せ`
- `取り扱い / 取扱い / 取扱`
- `振り込み / 振込み / 振込`

NFKCで吸収できる全角数字・半角括弧などは、aliasの大量追加ではなく正規化側で処理する。

## 応募歓迎タグの語尾ルール

中分類 `応募歓迎` でcanonicalが `歓迎` で終わるタグは、次のconfidenceで扱う。

### strict

- `X歓迎` → `XOK`
- `X歓迎` → `X大歓迎`
- `X歓迎` → `X積極採用`

理由: いずれもX層・条件を応募対象として積極的に受け入れることを明示しており、canonicalの「歓迎」条件を満たす。

既存のstrict aliasが `歓迎` で終わる場合も同じ語尾展開を行う。

例:

- `主婦（夫）歓迎` → `主婦（夫）OK`
- `初バイト歓迎` → `初バイトOK`

### loose

- `X歓迎` → `X可`

「可」は応募・条件を許容することは示すが、「歓迎」ほどの積極性を保証しないためlooseとする。

`X可` がlooseなら、共通語尾ルールで `Xも可` も同じloose confidenceで判定する。

既存のloose aliasが `歓迎` で終わる場合、その `OK / 大歓迎 / 積極採用 / 可` 派生もlooseのままとする。loose表現からconfidenceを上げない。

例:

- `主婦歓迎`（loose）→ `主婦OK` もloose
- `管理職経験歓迎`（loose）→ `管理職経験積極採用` もloose

### 個別例外

業界慣用上ほぼ同義と判断済みの既存strict aliasはその強さを維持する。

例:

- `未経験可` → `未経験者歓迎` のstrict alias

## 複合・区切り表現

複数属性をまとめたcanonicalでは、両方の意味を保持する区切り・括弧表現はstrictとする。

例:

- `シングルマザー・ファーザー歓迎`
  - `シングルマザー・シングルファーザー歓迎` → strict
  - `シングルマザー歓迎` → loose
  - `シングルファーザー歓迎` → loose
- `管理職・マネジメント経験歓迎`
  - 区切りだけの表記揺れ → strict
  - `管理職経験歓迎` / `マネジメント経験歓迎` → loose
- `主婦・主夫歓迎`
  - `主婦（夫）歓迎` / `主ふ歓迎` → strict
  - `主婦歓迎` / `主夫歓迎` → loose

## 活躍中・在籍と歓迎の関係

`活躍中` / `在籍` は、現在の職場構成を示す事実記述であり、応募歓迎を直接保証しない。

そのため第3版では歓迎タグへの横断alias化を行わない。

- 別canonicalがある場合はそのタグを優先する。
  - `障がい者活躍中` と `障がい者歓迎` は別タグ。
  - `女性活躍中` も独立タグ。
- 別canonicalがなくても、将来追加する場合は原則 `alias_loose` の個別レビュー対象とする。

## 求職者属性 + 応募表現

応募歓迎タグについて、属性・経験条件の直後に `応募` が入る表現はmatcherの共通variantとして処理する。alias列へ数百件の派生文字列を重複保存しない。

派生元は、canonical / strict alias / loose aliasのうち**基底の `X歓迎` 表現**だけ。

- `大歓迎` から再派生しない。
- `応募歓迎` から再派生しない。
- これにより `X大応募OK` や `X応募応募OK` のような不自然な再帰生成を防ぐ。

### 元のconfidenceを継承する

- `X応募歓迎`
- `X応募OK`
- `Xも応募OK`

strictな `X歓迎` からはstrict、looseな `X歓迎` からはloose。

例:

- `フリーター歓迎` → `フリーター応募OK` = strict
- `主婦歓迎`（複合タグに対するloose）→ `主婦応募OK` = loose

### 常にloose

- `X応募可`
- `Xも応募可`
- `X応募可能`
- `Xも応募可能`

「応募できる」ことは示すが、「歓迎」ほどの積極性は保証しないため。

既存の個別strict例外（例: `未経験可`）はそのまま維持するが、共通派生の `応募可` 系を自動的にstrictへ昇格させない。

### 対象外

このルールは中分類 `応募歓迎` のタグだけに適用する。

したがって `LINE応募可` / `Web応募可` / `電話応募可` のような応募手段を、求職者属性の歓迎タグへ変換しない。

## あり / なし の語尾variant

canonical / strict alias / loose aliasの末尾にある存在・不存在表現は、alias列へ大量保存せずmatcherで派生する。

### 同じconfidence

- `Xあり / X有り / Xアリ`
- `Xなし / X無し / Xナシ`

元がstrictならstrict、looseならlooseを維持する。

### 1文字の 有 / 無

`X有` / `X無` も同じconfidenceで扱うが、単純部分一致にはしない。

直後が次の場合だけ一致とする。

- 文末
- 空白・改行
- 句読点・区切り記号

これにより、

- `昇給有。` → `昇給あり`
- `転勤無／残業少なめ` → `転勤なし`

は拾う一方、

- `残業有無` → `残業あり` としない
- `駐車場無料` → `駐車場なし` としない

という安全性を保つ。

既存Sheetに登録済みの `有り / 無し / ナシ` aliasは互換性のため残す。今後は共通variantで吸収できる表記を機械的に追加し続ける必要はない。

## 活躍中 / 活躍 / 在籍

canonicalが `活躍中` で終わるタグについて、canonicalおよび `活躍中` で終わるaliasから次を派生する。

### 活躍

`X活躍中 → X活躍`

元のconfidenceを維持する。strictな表現からはstrict。

例:

- `女性活躍中 → 女性活躍`
- `外国人スタッフ活躍中 → 外国人スタッフ活躍`

### 在籍

`X活躍中 → X在籍`

在籍は「その属性の人がいる」ことは示すが、「活躍」までは保証しないため、常にloose / review。

例:

- `女性在籍`
- `外国人スタッフ在籍`

### 多数

`X多数` は対象や意味が曖昧になりやすいため、現時点では共通variantにしない。

`多数在籍` や `多数活躍中` も、必要になった時点でcontextを含めて別途設計する。


## 就業場所のフィールド別判定

就業場所タグは、求人情報を厳密に構造化するためではなく、広告配信・求職者とのマッチングに使う関心軸として扱う。

そのため、求人との合理的な関連性がある場所・施設は一定の意味的広がりを許容する。一方、文字列の偶然一致など、求人内容との意味的関連性がない判定は抑止する。

### フィールド信頼度

Advanced判定では `analyzeFields()` により入力列を構造化して渡す。

- primary: 勤務場所名1 / 勤務地
- identity: 仕事名 / Indeed用求人タイトル
- description: 仕事内容
- support: キャッチコピー、アピールポイント、画像説明文など
- weak: 勤務地住所、交通、面接地住所、応募資格、選考手順など

勤務場所名・仕事名は強い証拠として扱う。仕事内容は文脈を確認し、住所・交通・面接地などは原則として自動確定を弱める。

### 仕事内容のpositive context

次のような表現は就業場所の強い証拠として扱う。

- `Xで...`
- `Xにて...`
- `X内で...`
- `X勤務`
- `Xで勤務`
- `Xに勤務`
- `Xへ配属 / Xに配属`

例:

- `倉庫で商品の仕分け` → 倉庫 matched
- `工場にて部品検品` → 工場 matched
- `海辺のホテルで勤務` → 海 / ホテル matched

### 配送・納品・訪問など

配送先・納品先・訪問先であることは、求人との関連性がないとは限らない。そのため原則 `suppressed` ではなく `review` へ弱める。

例:

- `病院へ医薬品を配送` → 病院 review
- `コンビニへ商品を納品` → コンビニエンスストア review
- `倉庫から荷物を運び、工場で降ろす` → 倉庫 review / 工場 matched

勤務地を完全に復元するための経路・拠点推論までは行わない。

### 海の特殊ルール

`海` は1文字のため、通常のsubstring一致を行わない。

`海老名`、`東京海上日動`、`海浜幕張` などは海タグの根拠にしない。

`海の家`、`海辺`、`海沿い`、`ビーチ`、`マリンレジャー`、`海上作業` など、海が仕事環境として意味を持つ表現だけをsemantic patternとして扱う。

### 推論型タグ

`オフィス` のように求人中へ明示されにくいタグについて、職種・仕事内容だけからの推論は現時点では行わない。

- `オフィスで一般事務` → matched
- `一般事務、Excel入力、電話対応` → オフィスを自動推論しない

必要性と実データを確認してから別フェーズで追加する。
