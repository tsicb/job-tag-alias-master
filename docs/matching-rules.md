# マッチングルール

## 1. 基本思想

目的は「文字列が含まれていたら何でもタグ付与する」ことではなく、求人の意味に沿ったタグ候補を安定して抽出すること。

誤爆コストが高い項目では、取りこぼしを多少許容しても自動確定を保守的にする。

## 2. 前処理

推奨する最低限の正規化:

1. Unicode NFKC
2. Latin文字の小文字化
3. 不要な前後空白の除去
4. 改行・タブの取り扱いを統一

句読点や記号を全面的に削除すると、資格名・IT用語・給与表記の境界を壊す可能性があるため、過度な正規化は避ける。

## 3. alias

### alias_strict

canonicalとほぼ同義で、自動判定に比較的安全なもの。

例:

- `住宅手当あり` → `住宅手当` / `住居手当` / `家賃補助` / `住宅補助`
- `交通費支給` → `通勤手当` / `通勤費`
- `ゴールデンウィーク休暇あり` → `GW休暇` / `GW休み`

### alias_loose

近い意味だが、文脈により別意味にもなるもの。原則としてレビュー候補。

## 4. match_policy

### normal

canonicalまたはalias_strictが十分に具体的なら通常候補とする。除外語や否定表現があれば抑止する。

### strict_only

canonical自体が広すぎる場合に使用する。canonical単独のraw hitでは確定せず、より具体的なstrict表現を要求する。

### context

単語だけでは意味・関係性が確定できない場合に使用する。

現行の代表例:

- `採用`
- `介護`

就業場所タグも今後context候補として重点レビューする。

例:

- `病院へ配送` ≠ 勤務地が病院
- `学校向け営業` ≠ 勤務地が学校
- `工場へ納品` ≠ 勤務地が工場

### pattern

数値・形式・閾値で判断する。

現行例:

- 年間休日120日以上
- 残業月平均20時間以上
- 残業月平均20時間以内

## 5. 給与のpattern設計

給与系は特に保守的にする。

### 固定給25万円以上 / 固定給35万円以上

設計方針:

- 「固定給」と明示された金額のみ対象にする。
- `固定給26万円` は25万円以上の候補。
- `固定給35万円` は25万円以上と35万円以上の双方の候補になり得る。
- `月給26万円`、`基本給26万円`、`月収26万円` を固定給へ意味変換しない。
- 出稿者が給与用語を厳密に使っているとは限らないため、意味推測で閾値タグを追加しない。

これは第2版Sheetでは未反映の設計方針であり、次回pattern追加時の基準とする。

## 6. canonicalの包含関係

短いcanonicalが別canonicalの部分文字列になる場合、raw substring一致は危険。

例:

- `接客` / `接客なし`
- `英語` / `英語力不要`
- `深夜` / `深夜勤務なし`
- `海` / `海外勤務あり`
- `病院` / `動物病院`
- `Java` / `JavaScript`
- `Git` / `GitHub`

推奨処理:

1. より具体的な表現・除外語・否定表現を先に検査する。
2. broadなcanonicalは、その出現だけで自動確定しない。
3. 必要ならcontext / strict_onlyへ変更する。
4. 短い英数字はtoken境界判定を導入する。

## 7. 就業場所

就業場所カテゴリは、本文に施設名が登場しただけでは勤務場所と判断しない。

望ましい手掛かり:

- `勤務地：病院`
- `病院内で勤務`
- `勤務先は○○病院`
- `配属先：工場`

誤爆例:

- `病院へ医薬品を配送`
- `学校給食を配送`
- `工場向けの営業`

## 8. 判定結果の出し方

アプリ側では、単一のtrue/falseより次の情報を残すと検証しやすい。

- tag_code
- canonical
- hit_text
- hit_source: canonical / strict / loose / pattern
- decision: matched / review / suppressed
- reason
- surrounding_text（必要に応じて）

タグコードで重複除去する。

## 9. 精度改善

初期段階では過剰な自然言語解析を導入せず、実求人で見つかった失敗を次のいずれかへ分類して改善する。

- alias不足
- 除外語不足
- context化が必要
- strict_only化が必要
- pattern化が必要
- token境界判定が必要
- canonical同士の優先順位が必要
